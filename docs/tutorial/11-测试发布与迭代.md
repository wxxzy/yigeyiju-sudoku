# 11 · 测试、发布与迭代

> 本篇目标：理解项目的自检契约、商店物料体系、提审流程，以及改名重提的完整经过。

## 11.1 自检是行为规格说明书

`scripts/dev/selftest.lua` 有 577 行、14 组检查，覆盖：

| 组别 | 断言内容 |
|---|---|
| 生成 | 四档题目合法、唯一解、解与 solution 一致 |
| 填数 | 填错计数、同格同数字清除、笔记模式不写值 |
| 撤销 | 多格快照回滚、错误次数回滚、栈深上限 |
| 提示 | 两段式提示、理由存在、不直接填答案 |
| 通关 | 全盘正确才判 solved、结算数据完整 |
| 序列化 | serialize → restore 往返、故意用别的难度验证覆盖 |
| 存档 | 云不可用时的内存往返 |
| 成绩 | 首局保存、更慢不覆盖、更快刷新 |
| 题库 | 每档题量、唯一解、技巧等级、已知数区间 |
| 自动候选 | 候选与实际解无冲突 |
| 自动清笔记 | 填数后清理正确、可撤销 |
| 暂停 | 暂停时计时不累加 |
| 每日 | 确定性选题、连续打卡、同日重复不计 |
| 设置 | 循环切换、sanitize 非法值 |

跑法：

```bash
NODE_OPTIONS="" npx -y @taptap/maker@latest preview validate \
  --target-dir "<项目绝对路径>/sudoku" \
  --entry dev/selftest.lua --mode validate --json
```

**每次改完逻辑层都跑一遍**。这比人工试玩快得多，也能防止「修了 A 破坏了 B」。

## 11.2 发布配置

`.project/project.json` 的 `taptap_publish` 节点：

```json
{
  "title": "一格一局",
  "category": "trivia",
  "screen_orientation": "portrait",
  "collection_type": "sce",
  "app_platforms": "1,2",
  "app_id": 1012043,
  "developer_id": 492262,
  "miniapp_id": "tapmcnb6kejwswpr0o",
  "description": "...",
  "trial_note": "...",
  "gameplay_demo_video_id": 6039793
}
```

几个要点：

- `screen_orientation` 决定横竖屏——**发布配置而非代码**，改完要重新打包。
- `category` 在页面选的是「益智」，但本地快照写的是 `trivia`（问答）。商店生效值以开发者中心页面为准，本地快照只是同步记录，不要被它误导。
- `description` 和 `trial_note` 是商店文案，前者给玩家看，后者给审核看。
- `dc_publish_sync` 记录资料同步状态（`synced / dcVersion / dcStatus / baseFields`），`pending` 为空表示没有待推送字段。

## 11.3 商店物料清单

| 位置 | 规格 | 用途 |
|---|---|---|
| 游戏图标 | 512×512 | 无文字，改名不用重做 |
| 游戏截图 ×3 | 1080×1920（9:16） | 画面内不出现游戏名 |
| 宣传主图 | 1920×1080 | 详情页顶部 |
| 横版封面 | 1920×1080 | 含游戏名 |
| 竖版封面 | 1440×1440 | 含游戏名 |
| 方形宣传图 | 1440×1440 | 竖屏实机视频封面，含游戏名 |
| 实机测试视频 | MP4，≤1 分钟 | 手机录屏，画面内无窗口标题 |

**关键经验**：一旦改名，所有「图上有游戏名」的物料都要重做；图标、游戏截图、实机视频因为不含游戏名，可以保留。

## 11.4 提审流程

从开发者认证通过到上架，实际路径是：

```
1. Maker 发布面板：选发布厂商（需已认证）→ 核对物料 → 点「确认发布」
2. 开发者中心：全部游戏 → 唯一解/一格一局 → 商店 → 商店资料 → 提交审核
3. 状态从 INIT 变为「审核中」→ 等待 1–3 日（首次）
4. 审核通过 → 按设定时间上线
```

注意事项：

- 选「定时上线」时，首次必须设在当前时间 **6 小时之后**；
- 审核中资料无法编辑，只能「撤销审核」回到未发布；
- 小游戏前置备案是长周期流程（初审 12–16 工作日，全程约 20 工作日），如果需要，务必提前启动；
- 提交前在 TapTap 站内搜一下游戏名，避免重名——本项目就因此被驳回过一次。

## 11.5 改名重提的完整经过

这是一个真实案例，值得单独记录：

**背景**：首次提审因游戏名「唯一解」重名被驳回。

**处理步骤**：

1. **本地改名**：`.project/project.json` 的 `title` 和 `description`、`scripts/main.lua` 的 `CONFIG.Title`、上线文案；
2. **物料重做**：用 `make_promo.py` 重新生成 4 张带名字的图。把标题抽成 `TITLE` 常量，字号按 3→4 字 ×0.75 等比缩小，保持版式宽度一致；输出到新目录 `geyiju/`，旧图保留；
3. **验证**：下载线上 URL 与本地文件做像素比对（MAE=0），确认哪 4 张需要替换；本地 validate 60 帧 PASS；
4. **面板操作**：商店生效名称以 Maker 发布面板为准，本地 `project.json` 是远端快照且受 push-to-checkout 钩子保护，必须在面板改一次并重新上传物料；
5. **重新提审**：从「审核失败」状态编辑资料，再次提交。

**教训**：本地配置和商店生效值是两回事。改完本地不等于改完线上；反过来，面板改完也会同步回本地快照。两边要对齐。

## 11.6 上线后的迭代

- 每次更新都要重新提审，新版本号要高于旧版本（格式 `V x.y.z`）；
- 玩家反馈可以从 TapTap 游戏菜单的「问题反馈」收集，开发者可以按 TapID / 游戏 UID 查日志；
- 不要一次性更完所有内容，保持小步快跑的节奏；
- 逻辑层改动后先跑 `selftest`，再跑 `preview validate`，最后才构建提审。

## 11.7 完整开发流程回顾

```
需求 → 逻辑层设计（可单测）
     → 自检断言（先写测试）
     → UI 层实现（主题常量集中）
     → 主循环组装（RefreshAll 统一刷新）
     → 音效与手感打磨
     → preview validate + selftest
     → 构建 + 真机二维码验证
     → 物料准备 + 商店资料
     → 提审 → 上线 → 收集反馈 → 回到需求
```

## 11.8 本篇小结

- `selftest.lua` 是行为规格说明书，改逻辑必跑。
- 横竖屏、游戏名、商店文案属于发布配置，不在代码里。
- 商店生效值以 Maker 面板为准，本地 `project.json` 只是同步快照。
- 改名要连带重做所有含游戏名的物料，图标/截图/视频不用动。
- 提审前查重名、留足备案时间；上线后小步迭代。
